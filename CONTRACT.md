# Prototype module contract

All production code is dependency-free JavaScript, also compatible with Apps Script V8. No network, AI, storage of real data in source, or credential use. Core modules expose `var PPParser`, `var PPEngine`, and `var PPCatalog` globals and optionally `module.exports` for Node tests. The generated browser demo loads the shared core, an invented data artifact, workflow helpers and the app. The Apps Script bundle combines generated copies of the core with Main.gs.

## Records

- Project: `{id, name, length: 'Major'|'Minor'|'Either', types: string[], goals: string[], aliases: string[], enabled: boolean}`. Types canonical lowercase hands/head/heart/feet; goals canonical UN goal numbers as strings. `id` stable slug.
- Student: `{id, name, email, grade: 10|11|12, preference: 'Major'|'Minor'|'Not sure', choices: projectId[], types: string[], goals: string[], previous: projectId[], previousKnown: boolean, status: 'eligible'|'late'|'trip'|'leader'|'review', gender: 'Male'|'Female'|string|null, comments: string, celebration: string, destination: string, source: {sheet,row}, issues: string[]}`. `gender` is `null` with no Gender row or a blank one ("no gender on file"); any other value, such as `Nonbinary`, is kept as written and counts as neither Male nor Female. `celebration` is the kind of Celebration of Learning the student chose, and `destination` is a trip destination typed where the email goes (both `''` when there is none). `id` is the email; when two students share an email it is the email, `:` and the name, such as `jo@example.org:smith-jo`; a row with no email gets a sheet-row ID. `previousKnown` is false only when the student left last year's question blank. Comments are carried through only, never used for decisions. Every student ends up placed, excluded with a reason or in review with a reason, never silently dropped.
- Settings defaults: `{minSize:8,targetSize:11,maxSize:14,projectCount:23,minorProjects:8,minorMin:80,minorTarget:88,minorMax:96,allowMajorToMinor:true,checkedBeforeInferred:true,tieSeed:2026,useFriendRequests:false,balanceGender:false,followChecksOverTrack:false}`. `tieSeed`, `useFriendRequests` and `balanceGender` came in round 2, and `followChecksOverTrack` after it; a Settings tab without them uses these defaults. `minorTarget` must stay between `minorMin` and `minorMax`, but neither the sort nor the project suggestion uses it.
- Project choice keyed by id: `{run: boolean|null, length:'Major'|'Minor'|null, mustRun:boolean, leaders:studentId[], cannotRunWith:projectId[], maxSize:number|null}`. Empty means suggest. `maxSize` is a whole number from `minSize` to 14.

## Parser

`PPParser.prepare(tables, projects, options)` returns `{students,issues,stats}`. Tables: `[{name,grade,values:[][],backgrounds:[][]}]`; row1 header, backgrounds same coordinates CSS hex. Options may have `statusChanges:[{email,name,status,why}]`, `genders:[{email,gender}]`; either email may instead be a Student ID. `PPParser.goals` lists the 17 UN Sustainable Development Goals in order, written the usual way ("Industry, Innovation and Infrastructure"); matching ignores their punctuation. Gender is read ignoring case: M, Male and Boy are Male; F, Female and Girl are Female (`PPParser.genderOf`). Anything else is kept as written and never guessed, a blank row is no gender on file, and Gender rows that disagree are kept together (such as `Female / Male`), so the student counts as neither. When the Gender tab has rows, a `GENDER_NOT_COUNTED` issue gives two counts of the students who can be placed: those with no gender on file and those not listed as Male or Female. No message calls a student's gender unknown. Parse actual form headers and styles. Catalog is supplied. `PPParser.parseProjects(table)` returns `{projects,issues}`. Export public helpers as useful.

- Names. `PPParser.sameName(a, b)` is true for the same words in any order, or the same last name with a first name that is the same or starts with the other's first three letters (Nick and Nicholas). Names may be `Last, First` or `First Last`, with any spacing or capitals.
- One email. Forms whose names match are one student: the latest timestamp wins, a trip or leader color on any of them is kept, and a changed spelling is a warning. Clearly different names are separate eligible students with the flag "Two students sent their forms from the same email. Check that both answers are right." and a `SHARED_EMAIL` warning. A shared email's Gender row is not used for them; a row with the Student ID is. The same name and email in two grades stays in review (`IDENTITY_CONFLICT`).
- Hand-typed rows have a name but no email or timestamp. Each merges into the one form in its grade with a matching name. A green or uncolored row can instead merge into the only form in that grade with its last name, flagged "Matched a hand-typed row by last name only. Check it's the same student." A trip or leader row merges only by full name; without one it stays its own row with that status, however many forms share its last name. The row's trip, leader or green color wins; otherwise the form keeps its status. With no match the student is `late` with the flag "No response: check.", unless the row is a trip or leader, which keeps that status. When more than one form could match, or two rows match one form, nothing merges and the row goes to review with "More than one student matches this name." Every merge and no-response student is an issue (`HAND_TYPED_MERGED`, `HAND_TYPED_LAST_NAME`, `NO_RESPONSE`, `HAND_TYPED_UNCLEAR`).
- A hand-typed row whose email cell holds text that isn't an email, such as `COSTA RICA`, keeps it as `destination` in normal capitals (`Costa Rica`), also after the row merges into a form. Such a row that isn't colored blue (the trip color) is a `DESTINATION_NOT_TRIP` warning, so a person can check whether the student is on a trip.
- The question that starts "What do you want to do for your Celebration of Learning" becomes `celebration`: only the part before " - " when the answer has one, so "Project Fair - I want to..." is `Project Fair`. A form without the question gives `''`.
- Last year's project never blocks a student. Projects the answer names count as previous; anything it can't match adds "Couldn't match last year's project: <answer>." A grade whose form has no last-year question gets one `PREVIOUS_UNAVAILABLE` issue and no per-student flag.

## Engine

`PPEngine.defaults` settings object.
`PPEngine.interest(students,projects)` returns rows `{projectId,name,checked,aligned,byGrade:{10:number,11:number,12:number}}` counting eligible and late only, each combined project once.
`PPEngine.propose(students,projects,settings,choices)` returns `{projects,issues}` with selected Project records augmented by `finalLength:'Major'|'Minor'`, respecting exclusions/overrides.
`PPEngine.propose` chooses which projects run by score, ignoring length. The Minor slots take every running Minor-only project, then the running Either projects with the most Minor interest (Minor-preference and Not-sure students who checked them); every other Either project runs as a Major. Extra Minor-only projects make room for the next best Major or Either projects, and too few Minor-capable projects bring in the next best ones. Project choices override all of this.
`PPEngine.sort(students,projects,settings,choices,context)` returns `{assignments,projects,issues,checks,summary,friends,fingerprint}`. `context` is optional, so callers with four arguments keep working: `{previous: Assignment[] from the last run, locks: [{email,name,project1,project2,why,row}] from Locked placements, friends: [{name,classmate,request,use,namedEachOther,email,classmateEmail,row}] from Friend requests}`. In `friends`, `email` and `classmateEmail` take an email or a Student ID such as `jo@example.org:smith-jo`, like the Gender tab, so students who share an email can still be matched; a shared email alone is skipped with a warning. The sort runs in this order:
1. Locked students go exactly where their row says, even on the other track or in a project they didn't check. The reason starts "Locked in place:" and the row's `why`, or "Locked in place by hand." when it is blank, and never says who locked the student. A locked student at fit 6 gets no Fit 6 flag and no `LOW_FIT` warning, because a person chose the placement. A lock that breaks a rule is kept, with an error naming the student; a lock into a project that isn't running is an error and that student is placed by the normal rules. A lock into last year's project is a person's decision: its flag is "In last year's project because of a lock." and `PREVIOUS_PROJECT` is information. A project with a locked student is never cut.
2. Each leader listed for a running project is placed in it: both weeks for a Major, one week for a Minor. Leaders follow the project's length, count toward group size and may repeat last year's project. A leader on a trip, a freshman leader, in review, listed twice or listed for a project that isn't running gets an error naming them instead.
3. Every Minor-preference student does Minors. For each Not-sure student who isn't locked or leading, the sort counts the running Majors and Minors they checked, leaving out last year's projects. A student leans Minor with at least two Minors checked and at least as many Minors as Majors. Not-sure students are put in this order: those who lean Minor; then unpicked placements in Minors (2 minus the Minors checked, never below 0) minus unpicked placements in a Major (1 with no Majors checked, otherwise 0), smallest first; then Minors checked minus Majors checked, largest first; then sophomores, juniors and seniors; then students placed last; then tie order. Going down that order, a student who leans Minor does Minors while the Minor count is below the maximum, and while the count is still below the minimum the next students do too. Every other Not-sure student does a Major. The count includes locked Minor students and Minor leaders. The minimum and maximum are `minorMin` and `minorMax` narrowed to what the groups can hold, and when both can't be met the maximum wins. With `allowMajorToMinor`, Major-preference students move only while the Minor count is below its minimum, and each move is flagged. This replaced round 1's rule, which filled the Minors up to `minorTarget` with the Not-sure students who checked the most running Minors.
   A student's answer and checks disagree when, counting running projects they checked other than last year's, they said Major but checked no Major and at least one Minor, or said Minor but checked fewer than two Minors and at least one Major. Leaders, locked students and students who checked nothing never disagree. With `followChecksOverTrack`, these students are treated as Not sure. One placed on the other track gets "Said Major but checked only Minor projects, so placed by what they checked." or "Said Minor but checked mostly Majors, so placed by what they checked." at the end of the reason, and the flag "Said Major but placed in Minors they checked. Move them to a Major on their grade tab if you'd rather." or "Said Minor but placed in a Major they checked. Move them to two Minors on their grade tab if you'd rather." in place of the flag about the Minor minimum. With it FALSE no placement changes, and each of these students gets the flag "Said Major but checked no running Major." or "Said Minor but checked fewer than two running Minors." The flags are added after step 6, so the sentence ends the reason.
4. The rest are placed by a min-cost flow whose cost has three parts compared in order: (1) placing everyone, seniors first, then filling groups to the minimum; (2) how many seniors are in a project they didn't check, then juniors, sophomores and students placed last (green, or checked one project or none, flagged); (3) the fit number, seniors counted twice, then keeping the `previous` placement. Each level outweighs everything below it, so a senior never loses a project they checked to a younger student, and a senior's better fit never costs a younger student a project they checked. Students who are still tied go in a fixed shuffle: the order of `fingerprint([tieSeed, studentId])`. Groups split evenly. When any project has a `maxSize`, every group fills to `minSize` first. A Major with a `maxSize` keeps its even split (or `minSize`, if that's bigger) open to everyone, and its seats from there up to the `maxSize` are a second set of seats in the flow, at the same costs, that only students who checked the project reach; a student reaches them through one edge, so nobody takes two seats in one project. A `maxSize` below the even split caps the project. Locked students and leaders take open seats first. When a student can't be placed, the existing retry raises every size below its limit by one, open seats included, so the reserved seats never leave a student unplaced. A Minor with a `maxSize` keeps the rule from before: anyone can fill it up to the `maxSize`. Minor weeks are balanced, keeping locked weeks and last run's weeks.
   A student placed in a project they didn't check gets one sentence after that project's part of the reason (for a Minor, per week), with only the parts that apply: "None of their picks are running: X, Y." for checked projects that aren't running, "X was their project last year." (or "X and Y were their projects last year.") for ones the no-repeat rule blocks, "Their other picks were full." when other checked projects on their track were running and allowed, and "They checked no projects." Two more cover what those don't: "Their other picks run as Minors." (or Majors) when their running picks are all on the other track, and "Their other pick is their week 2 project." (or week 1) when a Minor student's one pick is their other week. A project they lead gets none, nor do locked students, moves by hand, or a project a friend request or "Not with" request moved them to, whose note says why.
5. With `useFriendRequests`, "Not with" pairs are moved apart: the student who wrote the request moves to their best other group, even when moving the classmate would cost less, and the move is flagged. Only when the writer is locked or leading does the classmate move instead, flagged "Moved because a classmate asked not to work with them."; if neither can move, the request is reported. Then a friend pass gives each student with a "With" request a named classmate where it can. Mutual pairs go first, then seniors, juniors and sophomores in tie order. When two Minor students share a Minor in different weeks, one of them first switches their two Minors between the weeks, which changes nobody's fit. Otherwise the pass tries moving the student, moving a classmate who named them back, then a swap with a third student. A change is kept only if askers drop at most one step in fit, nobody else drops or ends up in fewer projects they checked (judged by the projects they checked, not the fit number, whatever `checkedBeforeInferred` says), sizes, last year's projects and Minor pairs stay valid, no "Not with" pair ends up together and no met request breaks. Locked students and leaders never move.
6. With `balanceGender`, groups that break the gender rule (no Male students or at least three, and the same for Female) are fixed by swaps of two students or moves of one, in the same week and track. For each gender a group scores 2 with one student, 1 with two, and 0 with none or three and up. Each round considers every swap and every move that lowers the total score of the groups it touches and makes the first by smallest total drop in fit, then the least drop for seniors, then tie order, a move before a swap. A move keeps the group that grows at or under 12 students, or its project's `maxSize`, and the group that shrinks at or above `minSize`. Each student drops at most one step, no student ends up in fewer projects they checked (judged by the projects they checked, not the fit number), and no earlier rule breaks. Swapped students get "Swapped with a student in another group to balance the groups." and moved students "Moved to another group to balance the groups." Students not listed as Male or Female, locked students and leaders never move. In PP Check, groups with exactly one Male or one Female student are listed first.
`friends` lists every Friend requests row as `{row,name,classmate,request,result:'Together'|'Not together'|'Not applied',why}`.
Assignment: `{studentId,project1:projectId|null,project2:projectId|null,fit1:number|null,fit2:number|null,reason:string,flags:string[],status:'placed'|'excluded'|'review',locked?:true,movedByHand?:true}`. For Major, project1 only; minor project1 week1 and project2 week2. Exactly one Assignment per input Student including excluded/review. The sort sets `locked` on locked students, and Check again sets `movedByHand` on students whose projects changed since Sort.
`PPEngine.explain(student,projectIds,projects,settings,choices,byHand,locked,after)` returns `{fit1,fit2,reason,flags}` for those projects. `byHand` leaves out the flag about reaching the Minor minimum, and `locked` (`true` for a lock, `'hand'` for a move by hand) also leaves out the Fit 6 flag and, for a project from last year without a leader exception, adds "In last year's project because of a lock." or "In last year's project because of a move by hand." `after[i]`, when given, ends the reason for project i; the sort passes the sentences above, and Check again passes none. The sort adds flags for leaders, students placed last and moves for friends or gender.
`PPEngine.locks(students,projects,rows)` resolves Locked placements rows: a student by email or Student ID (ignoring case and spaces), or by name when the email is blank; a project by name, ID or MAJ-/MIN- label. It returns `{byStudent,issues}`, with `byStudent[id]` as `{project1,project2,row,why}`; rows it can't match are errors.
`PPEngine.friends(students,projects,assignments,settings,rows,choices)` reports where each friend request stands for a set of placements without moving anyone, for Check again.
`PPEngine.summarize(students,projects,assignments,settings,choices)` returns the Summary below. `settings` and `choices` are optional; with them it adds `tracks`.
Checks: `{code,severity:'error'|'warning'|'info',message,studentId?:string,projectId?:string,week?:number}[]`.
Summary: `{total,eligible,placed,excluded,needsReview,majorStudents,minorStudents,projectCount,minorProjectCount,fitCounts:{1:number,...,6:number},byGrade:{10|11|12:{placed,meanFit,major:{checked,notChecked},minor:{bothChecked,oneChecked,noneChecked},fits:{1:number,...,6:number}}},groups:[{id,name,length,sizes}]}`. The sort adds `friends:{used,withMet,withUnmet,studentsWith,studentsMet,notWithBroken}`. With settings, `tracks:{disagree,followChecks}` counts the students whose answer and checks disagree (leaving out locked students, students moved by hand and leaders) and says whether `followChecksOverTrack` is on.
`PPEngine.check(students,selectedProjects,assignments,settings,choices,context)` returns independent Checks array, evaluating actual output, detecting manually changed invalid assignments. A Major in one column and a Minor in the other is a `MIXED_TRACKS` error. For a `locked` or `movedByHand` assignment, a Major/Minor preference change is information, a fit 6 is not a `LOW_FIT` warning, and last year's project is a `PREVIOUS_PROJECT` information note saying "In last year's project because of a lock." or "... because of a move by hand." `PREVIOUS_PROJECT` stays an error ("Student repeats a previous project without a leader exception.") when the sort itself put the student there. A preference change that `followChecksOverTrack` made is information too, ending "Placed by what they checked." Group limits use each project's `maxSize`. When gender data exists, every group that breaks the gender rule is a `GENDER_BALANCE` warning counting Male and Female students and saying how many are not listed as Male or Female and how many have no gender on file, such as "a: 9 Male and 1 Female students (1 not listed as Male or Female)." in PP Check. With `useFriendRequests` and `context.friends`, a "Not with" pair in one group is a `NOT_WITH_TOGETHER` error naming both students. `PPEngine.fit(student,project,settings)` returns `{tier,checked,typeMatch,goalMatch,reason}`. The reason names each matching UN goal from `PPParser.goals` (goal n is its nth name), such as "UN goal match (Industry, Innovation and Infrastructure)", and capitalizes types, such as "type match (Head, Hands)". `PPEngine.fingerprint(value)` stable reproducibility fingerprint (not cryptographic).

## Browser

Two main views: choose projects, then place students. Supporting panels expose source records, rules, grouped findings, individual evidence and rosters. A five-step walkthrough appears on fresh page loads. Changes invalidate results until rerun with a reason. CSV export escapes formula-like strings and labels results proposed. Comments remain available but do not affect matching. There are no runtime network calls, external fonts or browser persistence.

The public builder uses `preview/demo-data.js` to create invented records in `dist/assets/demo-data.js` with `mode: 'demo'`. The private entry at `preview/index.html` instead requires `../../case-f-private/attached-data.js` with `mode: 'attached'`. Both enforce schemaVersion 1 and validate records; missing or mismatched data stops loading. The private payload stays outside the repository and public build.

## Adapter

Google Sheets menu: Setup, Prepare students, Count interest, Sort, Check again, Make practice data. Source tabs Senior/Junior/Sophomore/Projects read only. Outputs prefixed PP, plus the control tabs Settings, Project choices, Status changes, Gender, Locked placements and Friend requests. Setup adds missing tabs, Settings rows and columns (Max size, Faculty and Location in Project choices; Tie seed and Run by in PP Run log) and never changes a value that's there. Faculty can list several names separated by commas, and Location is free text. The sort never reads either; they appear on PP Master list, PP Projects and the project tabs, read fresh on each Sort and Check again, and blank stays blank. Friend requests is read by header name and its Comment column is never read. Runtime must refuse malformed settings and missing required sources with descriptive errors. Preserve editable settings and run log on reruns. Log reason and fingerprint. Output MAJ-/MIN- grade master columns Project #1 / Project #2 plus project rosters.

Every flag and student issue is either information or needs a decision. Information: "Historical project not on current list...", "Latest timestamped submission retained...", "Green status...", "Checked only one project, so placed after everyone else." and "Checked no projects, so placed after everyone else.", "Only one current project was checked...", "Leading ..., so placed there.", "Previous-project exception: named leader of ...", "In last year's project because of a lock." or "... a move by hand.", and the reason sentences for locks, gender and friend moves if they were ever flags. Everything else needs a decision, and so does everything for a student in review. PP Needs you lists a student only with something that needs a decision, or in review, and its Flags column (the assignment's flags, then the student's issues) shows only those. The grade tabs' Review flags column shows the assignment's flags with the same filter. The run snapshot keeps every flag and PP Students every issue. A Major shows its MAJ- label in both columns; a Minor shows two different MIN- labels. Every Project #1 and Project #2 cell has a dropdown of running labels and can be cleared. Student comments appear only in PP Students, never in the grade, group or review tabs.

PP Senior, PP Junior and PP Sophomore stay the tabs Mr. Litowitz edits. Sort writes these as well, and Check again rebuilds them from the grade tabs:
- PP Start here, the first tab: the title "Project: Pomfret 2026-27: proposed groups", "Last sorted:" with the time, who ran it and the reason, the same values Sort writes to PP Run log (after Check again read from PP Run log's newest row, followed by "Checked again: <time> by <who>."), what each main tab holds, what a UN goal match means, how to move a student, and not to edit the rebuilt tabs. Column A is 700 px and wraps.
- PP Master list, for reading and printing: SENIORS, JUNIORS and SOPHOMORES sections, each a bold title, a header row (Name, Project #1, Project Faculty, Project #2, Project Faculty, Why) and its placed students by last name ("Last, First" or "First Last"; Jr., Sr. and II to IV are skipped). A Major shows its MAJ- label in both project columns; a Minor shows week 1 then week 2.
- PP Projects: one row per running project, Majors then Minors, each by name, with #, Project (its label), Location, Faculty, Week 1, Week 2 (the group sizes; a Major's are the same), Male, Female, Seniors, Juniors, Sophomores and Picked it (students in the group who checked it); a Minor's counts read "week 1 / week 2". Flags: "Over 12 students" for a project with no Max size, "Under 8 students" (the minimum), and "Fewer than 3 of one gender" when the group has 1 or 2 of a gender, with " in week N" for a Minor.
- PP Group tabs, like last year's rosters: the project's label in bold, "Faculty: ...", "Location: ...", then a header row (Student, Grade, Celebration of Learning, Why) and the students, seniors first and then by last name, ending in a bold "TOTAL - N Students". A Minor has a block for each week, headed "GROUP 1 (week 1)" and "GROUP 2 (week 2)", ending in "GROUP 1 TOTAL - N Students" and "GROUP 2 TOTAL - N Students". A tab is named "PP Group", its number and the project's name, with a slash turned into " - ", other characters Sheets refuses turned into spaces and never two spaces in a row, such as "PP Group 02 Biomimicry - 3D Adaptive Tools". Nothing reads these tabs back. PP Project tabs lists them, and on each run a PP Group tab from an earlier run that this run doesn't write is deleted: one PP Project tabs listed, or one under round 2's name for a running project (slashes as spaces), so a rerun never leaves both.
- PP Not placed: every student who isn't placed, by grade and last name, with Name, Grade, Status (Excluded or Needs review) and Why: "ExEd trip" (or "ExEd trip: Japan" with a destination), "Freshman leader", or the review reason and, for a student in review, their issues.

Formatting. PP tabs never auto-resize. `write()` sets each column's width from its header with one table: # 45; Grade, Fit #1, Fit #2 70; Status, Severity, Preference, Use 90; Week 1, Week 2, Male, Female, Seniors, Juniors, Sophomores, Picked it 85; Location 130; Faculty, Project Faculty 160; Celebration of Learning 190; Name, Student, Classmate 210; Student ID, Email, Classmate email, Code 230; Project, Project #1, Project #2, Project 1, Project 2 270 (300 on PP Projects); Metric 420; Value 220; Why, Reason, Message, Student comment, Comment, Issues 560; Flags, Review flags 420 (300 on PP Projects); anything else 140, one `setColumnWidths` call per run of equal widths. `writeLayout()` takes its widths from the caller: PP Master list 220, 270, 150, 270, 150, 560; PP Group tabs 220, 70, 190, 620; PP Start here 700. Tabs that Setup and Make practice data create still size to their text. Every written cell is aligned to the top; columns 420 px and wider wrap and the rest don't; the #, Grade, Fit and count columns are centered. `write()` clears old formatting before writing, as `writeLayout()` does, and the grade tabs' dropdowns are set after it; Check again edits grade-tab cells in place. Header rows are maroon (#9e2132, white, bold) and frozen; PP Needs you, PP Projects and the grade tabs also freeze their first two columns. On PP Master list the grade titles are bold, size 12 and shaded #F4E4E6. On the PP Group tabs the label is bold and size 14, Faculty and Location are gray #666666, the GROUP rows are bold and shaded #F4E4E6 and the TOTAL rows bold and shaded #EEEEEE; each style is one `getRangeList` call. PP Projects has light gray #D9D9D9 borders on every cell, and a row with flags is shaded #FCE8E6 from Project to Flags with its flags in #9E2132.

Tab order after Sort and Check again: PP Start here, PP Master list, PP Projects, PP Needs you, PP Not placed, PP Summary, the PP Group tabs by number, PP Senior, PP Junior, PP Sophomore, the other PP tabs, then every other tab in the order it was in. Only tabs out of place move, and a tab that doesn't start with "PP " is never renamed or deleted. PP Start here, PP Master list, PP Projects, PP Needs you, PP Not placed and the PP Group tabs are colored #9E2132 and the other PP tabs #999999; other tabs keep their color. After Sort PP Start here is showing; after Check again, the tab that was showing before.

Check again and Sort first save moves: each student whose Project #1 or #2 differs from PP Run snapshot gets a row in Locked placements (Email or Student ID, Name, Project 1, Project 2, Locked by from the active user's email or "unknown", When, Why "Moved by hand"). Saving compares placements only, so it works after Settings, Project choices or the forms change, and a matching row is left alone. Sort passes the snapshot's placements as `context.previous`, the lock rows and the friend rows, and logs the tie seed and Run by. Check again then reads a Major as the same label twice, or one label and a blank. For each student whose projects changed since Sort, it recomputes Status, Fit #1, Fit #2, Reason (starting "Moved by hand.") and Review flags with `PPEngine.explain`, writes them back and adds an information note; moving between Major and Minors is information. Unchanged rows are not rewritten. The engine checks report any rule a move breaks, and a lock row the grade tab doesn't show is a warning. A student Sort placed with a lock stays `locked` in these checks. Locked placements' Why column reaches the engine as the lock's `why`. Then it rebuilds PP Master list, PP Projects, PP Group tabs, PP Not placed, PP Summary, PP Needs you, PP Seniors to check and PP Friend check from the grade tabs, without sorting. PP Needs you takes each student's flags from the grade tab's Review flags, which hold only the flags that need a decision, so the rows for answers and checks that disagree stay until the student is moved; a moved student is locked and no longer counts. Nothing else reads Review flags back. PP Summary has a line with the number of students whose answer and checks disagree and whether `followChecksOverTrack` is on. The manifest's scopes are the current spreadsheet and `userinfo.email`, for Locked by and Run by. Google Sheets live execution remains unverified until run in school account.
