# Prototype module contract

All production code is dependency-free JavaScript, also compatible with Apps Script V8. No network, AI, storage of real data in source, or credential use. Core modules expose `var PPParser`, `var PPEngine`, and `var PPCatalog` globals and optionally `module.exports` for Node tests. The generated browser demo loads the shared core, an invented data artifact, workflow helpers and the app. The Apps Script bundle combines generated copies of the core with Main.gs.

## Records

- Project: `{id, name, length: 'Major'|'Minor'|'Either', types: string[], goals: string[], aliases: string[], enabled: boolean}`. Types canonical lowercase hands/head/heart/feet; goals canonical UN goal numbers as strings. `id` stable slug.
- Student: `{id, name, email, grade: 10|11|12, preference: 'Major'|'Minor'|'Not sure', choices: projectId[], types: string[], goals: string[], previous: projectId[], previousKnown: boolean, status: 'eligible'|'late'|'trip'|'leader'|'review', gender: 'Male'|'Female'|null, comments: string, source: {sheet,row}, issues: string[]}`. `id` is the email; when two students share an email it is the email, `:` and the name, such as `jo@example.org:smith-jo`; a row with no email gets a sheet-row ID. `previousKnown` is false only when the student left last year's question blank. Comments are carried through only, never used for decisions. Every student ends up placed, excluded with a reason or in review with a reason, never silently dropped.
- Settings defaults: `{minSize:8,targetSize:11,maxSize:14,projectCount:23,minorProjects:8,minorMin:80,minorTarget:88,minorMax:96,allowMajorToMinor:true,checkedBeforeInferred:true,tieSeed:2026,useFriendRequests:false,balanceGender:false}`. `tieSeed`, `useFriendRequests` and `balanceGender` came in round 2; a Settings tab without them uses these defaults.
- Project choice keyed by id: `{run: boolean|null, length:'Major'|'Minor'|null, mustRun:boolean, leaders:studentId[], cannotRunWith:projectId[], maxSize:number|null}`. Empty means suggest. `maxSize` is a whole number from `minSize` to 14.

## Parser

`PPParser.prepare(tables, projects, options)` returns `{students,issues,stats}`. Tables: `[{name,grade,values:[][],backgrounds:[][]}]`; row1 header, backgrounds same coordinates CSS hex. Options may have `statusChanges:[{email,name,status,why}]`, `genders:[{email,gender}]`; either email may instead be a Student ID. Gender is read ignoring case: M, Male and Boy are Male; F, Female and Girl are Female; anything else, or a blank, is unknown and is never guessed (`PPParser.genderOf`). Parse actual form headers and styles. Catalog is supplied. `PPParser.parseProjects(table)` returns `{projects,issues}`. Export public helpers as useful.

- Names. `PPParser.sameName(a, b)` is true for the same words in any order, or the same last name with a first name that is the same or starts with the other's first three letters (Nick and Nicholas). Names may be `Last, First` or `First Last`, with any spacing or capitals.
- One email. Forms whose names match are one student: the latest timestamp wins, a trip or leader color on any of them is kept, and a changed spelling is a warning. Clearly different names are separate eligible students with the flag "Two students sent their forms from the same email. Check that both answers are right." and a `SHARED_EMAIL` warning. A shared email's Gender row is not used for them; a row with the Student ID is. The same name and email in two grades stays in review (`IDENTITY_CONFLICT`).
- Hand-typed rows have a name but no email or timestamp. Each merges into the one form in its grade with a matching name. A green or uncolored row can instead merge into the only form in that grade with its last name, flagged "Matched a hand-typed row by last name only. Check it's the same student." A trip or leader row merges only by full name; without one it stays its own row with that status, however many forms share its last name. The row's trip, leader or green color wins; otherwise the form keeps its status. With no match the student is `late` with the flag "No response: check.", unless the row is a trip or leader, which keeps that status. When more than one form could match, or two rows match one form, nothing merges and the row goes to review with "More than one student matches this name." Every merge and no-response student is an issue (`HAND_TYPED_MERGED`, `HAND_TYPED_LAST_NAME`, `NO_RESPONSE`, `HAND_TYPED_UNCLEAR`).
- Last year's project never blocks a student. Projects the answer names count as previous; anything it can't match adds "Couldn't match last year's project: <answer>." A grade whose form has no last-year question gets one `PREVIOUS_UNAVAILABLE` issue and no per-student flag.

## Engine

`PPEngine.defaults` settings object.
`PPEngine.interest(students,projects)` returns rows `{projectId,name,checked,aligned,byGrade:{10:number,11:number,12:number}}` counting eligible and late only, each combined project once.
`PPEngine.propose(students,projects,settings,choices)` returns `{projects,issues}` with selected Project records augmented by `finalLength:'Major'|'Minor'`, respecting exclusions/overrides.
`PPEngine.propose` chooses which projects run by score, ignoring length. The Minor slots take every running Minor-only project, then the running Either projects with the most Minor interest (Minor-preference and Not-sure students who checked them); every other Either project runs as a Major. Extra Minor-only projects make room for the next best Major or Either projects, and too few Minor-capable projects bring in the next best ones. Project choices override all of this.
`PPEngine.sort(students,projects,settings,choices,context)` returns `{assignments,projects,issues,checks,summary,friends,fingerprint}`. `context` is optional, so callers with four arguments keep working: `{previous: Assignment[] from the last run, locks: [{email,name,project1,project2,why,row}] from Locked placements, friends: [{name,classmate,request,use,namedEachOther,email,classmateEmail,row}] from Friend requests}`. In `friends`, `email` and `classmateEmail` take an email or a Student ID such as `jo@example.org:smith-jo`, like the Gender tab, so students who share an email can still be matched; a shared email alone is skipped with a warning. The sort runs in this order:
1. Locked students go exactly where their row says, even on the other track or in a project they didn't check. The reason starts "Locked in place:" and the row's `why`, or "Locked in place by hand." when it is blank, and never says who locked the student. A locked student at fit 6 gets no Fit 6 flag and no `LOW_FIT` warning, because a person chose the placement. A lock that breaks a rule is kept, with an error naming the student; a lock into a project that isn't running is an error and that student is placed by the normal rules. A project with a locked student is never cut.
2. Each leader listed for a running project is placed in it: both weeks for a Major, one week for a Minor. Leaders follow the project's length, count toward group size and may repeat last year's project. A leader on a trip, a freshman leader, in review, listed twice or listed for a project that isn't running gets an error naming them instead.
3. Every Minor-preference student does Minors. Not-sure students are ranked by how many running Minor projects they checked, most first, then sophomores, juniors and seniors, and fill the Minor spots up to `minorTarget`, never above `minorMax`, counting locked and leading Minor students. With `allowMajorToMinor`, Major-preference students move only while the Minor count is below its minimum, and each move is flagged.
4. The rest are placed by a min-cost flow whose cost has three parts compared in order: (1) placing everyone, seniors first, then filling groups to the minimum; (2) how many seniors are in a project they didn't check, then juniors, sophomores and students placed last (green, or checked one project or none, flagged); (3) the fit number, seniors counted twice, then keeping the `previous` placement. Each level outweighs everything below it, so a senior never loses a project they checked to a younger student, and a senior's better fit never costs a younger student a project they checked. Students who are still tied go in a fixed shuffle: the order of `fingerprint([tieSeed, studentId])`. Groups split evenly, except that a project with `maxSize` may grow to it while every group still fills to `minSize` first. Minor weeks are balanced, keeping locked weeks and last run's weeks.
5. With `useFriendRequests`, "Not with" pairs are moved apart (whoever loses less fit; on a tie, the one placed later; the move is flagged), then a friend pass gives each student with a "With" request a named classmate where it can. Mutual pairs go first, then seniors, juniors and sophomores in tie order. When two Minor students share a Minor in different weeks, one of them first switches their two Minors between the weeks, which changes nobody's fit. Otherwise the pass tries moving the student, moving a classmate who named them back, then a swap with a third student. A change is kept only if askers drop at most one step in fit, nobody else drops, sizes, last year's projects and Minor pairs stay valid, no "Not with" pair ends up together and no met request breaks. Locked students and leaders never move.
6. With `balanceGender`, groups that break the gender rule (no Male students or at least three, and the same for Female) are fixed by swaps in the same week and track: each student drops at most one step, no student moves from a project they checked to one they didn't, no earlier rule breaks, smallest total drop first, seniors' fit dropped last, ties in tie order. Unknown genders never move. In PP Check, groups with exactly one Male or one Female student are listed first.
`friends` lists every Friend requests row as `{row,name,classmate,request,result:'Together'|'Not together'|'Not applied',why}`.
Assignment: `{studentId,project1:projectId|null,project2:projectId|null,fit1:number|null,fit2:number|null,reason:string,flags:string[],status:'placed'|'excluded'|'review',locked?:true,movedByHand?:true}`. For Major, project1 only; minor project1 week1 and project2 week2. Exactly one Assignment per input Student including excluded/review. The sort sets `locked` on locked students, and Check again sets `movedByHand` on students whose projects changed since Sort.
`PPEngine.explain(student,projectIds,projects,settings,choices,byHand,locked)` returns `{fit1,fit2,reason,flags}` for those projects. `byHand` leaves out the flag about reaching the Minor minimum, and `locked` (a lock, or a move by hand) also leaves out the Fit 6 flag. The sort adds flags for leaders, students placed last and moves for friends or gender.
`PPEngine.locks(students,projects,rows)` resolves Locked placements rows: a student by email or Student ID (ignoring case and spaces), or by name when the email is blank; a project by name, ID or MAJ-/MIN- label. It returns `{byStudent,issues}`, with `byStudent[id]` as `{project1,project2,row,why}`; rows it can't match are errors.
`PPEngine.friends(students,projects,assignments,settings,rows,choices)` reports where each friend request stands for a set of placements without moving anyone, for Check again.
`PPEngine.summarize(students,projects,assignments)` returns the Summary below.
Checks: `{code,severity:'error'|'warning'|'info',message,studentId?:string,projectId?:string,week?:number}[]`.
Summary: `{total,eligible,placed,excluded,needsReview,majorStudents,minorStudents,projectCount,minorProjectCount,fitCounts:{1:number,...,6:number},byGrade:{10|11|12:{placed,meanFit,major:{checked,notChecked},minor:{bothChecked,oneChecked,noneChecked},fits:{1:number,...,6:number}}},groups:[{id,name,length,sizes}]}`. The sort adds `friends:{used,withMet,withUnmet,studentsWith,studentsMet,notWithBroken}`.
`PPEngine.check(students,selectedProjects,assignments,settings,choices,context)` returns independent Checks array, evaluating actual output, detecting manually changed invalid assignments. A Major in one column and a Minor in the other is a `MIXED_TRACKS` error. For a `locked` or `movedByHand` assignment, a Major/Minor preference change is information and a fit 6 is not a `LOW_FIT` warning. Group limits use each project's `maxSize`. When gender data exists, every group that breaks the gender rule is a `GENDER_BALANCE` warning counting only known genders and saying how many are unknown. With `useFriendRequests` and `context.friends`, a "Not with" pair in one group is a `NOT_WITH_TOGETHER` error naming both students. `PPEngine.fit(student,project,settings)` returns `{tier,checked,typeMatch,goalMatch,reason}`. `PPEngine.fingerprint(value)` stable reproducibility fingerprint (not cryptographic).

## Browser

Two main views: choose projects, then place students. Supporting panels expose source records, rules, grouped findings, individual evidence and rosters. A five-step walkthrough appears on fresh page loads. Changes invalidate results until rerun with a reason. CSV export escapes formula-like strings and labels results proposed. Comments remain available but do not affect matching. There are no runtime network calls, external fonts or browser persistence.

The public builder uses `preview/demo-data.js` to create invented records in `dist/assets/demo-data.js` with `mode: 'demo'`. The private entry at `preview/index.html` instead requires `../../case-f-private/attached-data.js` with `mode: 'attached'`. Both enforce schemaVersion 1 and validate records; missing or mismatched data stops loading. The private payload stays outside the repository and public build.

## Adapter

Google Sheets menu: Setup, Prepare students, Count interest, Sort, Check again, Make practice data. Source tabs Senior/Junior/Sophomore/Projects read only. Outputs prefixed PP, plus the control tabs Settings, Project choices, Status changes, Gender, Locked placements and Friend requests. Setup adds missing tabs, Settings rows and columns (Max size in Project choices; Tie seed and Run by in PP Run log) and never changes a value that's there. Friend requests is read by header name and its Comment column is never read. Runtime must refuse malformed settings and missing required sources with descriptive errors. Preserve editable settings and run log on reruns. Log reason and fingerprint. Output MAJ-/MIN- grade master columns Project #1 / Project #2 plus project rosters. A Major shows its MAJ- label in both columns; a Minor shows two different MIN- labels. Every Project #1 and Project #2 cell has a dropdown of running labels and can be cleared. Student comments appear only in PP Students, never in the grade, group or review tabs.

Check again and Sort first save moves: each student whose Project #1 or #2 differs from PP Run snapshot gets a row in Locked placements (Email or Student ID, Name, Project 1, Project 2, Locked by from the active user's email or "unknown", When, Why "Moved by hand"). Saving compares placements only, so it works after Settings, Project choices or the forms change, and a matching row is left alone. Sort passes the snapshot's placements as `context.previous`, the lock rows and the friend rows, and logs the tie seed and Run by. Check again then reads a Major as the same label twice, or one label and a blank. For each student whose projects changed since Sort, it recomputes Status, Fit #1, Fit #2, Reason (starting "Moved by hand.") and Review flags with `PPEngine.explain`, writes them back and adds an information note; moving between Major and Minors is information. Unchanged rows are not rewritten. The engine checks report any rule a move breaks, and a lock row the grade tab doesn't show is a warning. A student Sort placed with a lock stays `locked` in these checks. Locked placements' Why column reaches the engine as the lock's `why`. Then it rebuilds PP Group tabs, PP Summary, PP Needs you, PP Seniors to check and PP Friend check from the grade tabs, without sorting. The manifest's scopes are the current spreadsheet and `userinfo.email`, for Locked by and Run by. Google Sheets live execution remains unverified until run in school account.
